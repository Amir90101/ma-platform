# Техническая архитектура

Одно приложение на Next.js с базой и бэкендом на Supabase. Админка и публичная страница живут в одном репозитории и одном деплое.

## Стек

| Часть | Выбор | Зачем |
| --- | --- | --- |
| Фронтенд | Next.js (App Router), TypeScript strict, Tailwind, shadcn/ui | Публичная страница рендерится на сервере и нормально открывается в превью WhatsApp и Instagram |
| Карта зала | react-konva | Перетаскивание, поворот и масштаб фигур на холсте |
| База | Supabase Postgres | Ограничения на уровне базы против двойных броней |
| Авторизация | Supabase Auth, email и пароль | Для владельцев и администраторов. Гости без аккаунтов |
| Права доступа | Row Level Security | Каждое заведение видит только свои данные |
| Живые статусы | Supabase Realtime | Столы и новые брони обновляются без перезагрузки |
| Фото | Supabase Storage | Фото заведения для публичной страницы |
| Фоновые задачи | pg_cron | Отметка неявок |
| Защита формы | Cloudflare Turnstile | Против ботов на публичной форме брони |
| Мониторинг ошибок | Sentry (`@sentry/nextjs`) | Ошибки сервера и браузера; телефоны гостей и токены `/b/{token}` вычищаются до отправки |
| Переводы | next-intl | Русский сейчас, казахский позже без переделки |
| Тесты | Vitest, Playwright, pgTAP | Юнит, e2e, тесты базы и RLS |
| Хостинг фронтенда | Vercel | Деплой из GitHub |

Edge Functions в первой версии не используются.

## Где живёт логика

Правило: всё, что меняет деньги, время или занятость стола, делает одна SQL-функция в одной транзакции. Клиент только вызывает её.

| Слой | Что там | Почему |
| --- | --- | --- |
| Postgres RPC (`supabase/migrations`) | Старт, пауза, перенос и закрытие сеанса, создание и смена статуса брони, расчёт суммы, открытие и закрытие смены, свободные окна | Атомарность. Два администратора не запустят один стол дважды |
| Next.js Server Actions | Формы админки: профиль, тарифы, карта зала, сотрудники. Вызов RPC от имени пользователя | RLS применяется автоматически, потому что запрос идёт с JWT пользователя |
| Next.js Route Handlers | Публичная бронь: проверка Turnstile, лимит по телефону и IP, затем вызов RPC `create_public_booking` | Turnstile проверяется только на сервере |
| pg_cron | Отметка неявок | Работает, даже если никто не открыл админку |

Функции, которые вызывает пользователь, объявлены как `security invoker`, чтобы работал RLS. Исключение — RPC для сеансов, смен, оплат и броней: в эти таблицы пользователь напрямую не пишет, поэтому функции `security definer` и сами проверяют участника заведения. Функции для публичной страницы объявлены как `security definer` и возвращают только безопасные поля. Подробности и список функций в `docs/DATABASE.md`.

## Интерфейс

- Ориентир по стилю — приложения компьютерных клубов (LanGame): тёмное меню, светлое рабочее поле с белыми карточками, красный `--primary` для главных действий, крупные скругления. Шрифт Onest (кириллица и казахские буквы, табличные цифры). Токены — в `src/app/globals.css`, тень карточек — `shadow-card`.
- Две темы. Светлая — админка. Тёмная (класс `dark` + `public-dark` на обёртке) — страницы гостя `/[slug]` и `/b/[token]`, первый экран главной.
- Статусы мест — отдельные токены `--status-free|busy|paused|booked` (и `-soft` для фона): одни и те же на карте, в списках, в легенде и в бронях. Цвета холста Konva в `hall-canvas.tsx` повторяют эти токены, у холста светлая и тёмная палитры.
- Схема зала на рабочем экране и у гостя тёмная и обрезана по фигурам (`src/lib/hall/fit.ts`): пустые края зала не показываем, места на телефоне крупнее. Редактор показывает зал целиком.
- Админка заведения — каркас `src/app/app/[venueId]/layout.tsx`: чёрная боковая панель на компьютере, чёрные нижние вкладки на телефоне и планшете, общая верхняя полоса с пользователем. Разделы зависят от роли (`src/lib/venue-nav.ts`). Главная заведения — «Обзор» на сегодня; у владельца там же список «Настройка заведения», пока не всё готово.
- Заголовок экрана — `PageHeader`, карточка с цифрой — `StatCard`, список шагов — `SetupChecklist` (`src/components/app-shell/`).
- Тариф на время выбирают карточками с ценой — и при запуске места, и на странице брони. Выбранная карточка заливается тёмным.
- Кнопки и поля крупнее стандартных shadcn: админкой пользуются за стойкой, часто с планшета.
- Публичная страница: галерея фото (свайп, точки, стрелки на компьютере), карточка заведения с кнопкой брони, бронь по шагам с кнопкой шага внизу экрана, справа на компьютере цены, часы и правила. Обложка — первое фото; владелец выбирает её в настройках («Сделать обложкой»).

## Realtime

Админка подписывается на изменения своего заведения:

- `session_segments` и `sessions` с фильтром `venue_id` — статусы столов на карте.
- `shifts` с фильтром `venue_id` — полоса смены над картой.
- `bookings` с фильтром `venue_id` — новые онлайн-брони и отмены. Новая онлайн-бронь показывается уведомлением со звуком. Лента броней перечитывается при любом изменении броней заведения.

Подписку держит хук `useVenueRealtime(venueId, tables)`: при событии он перечитывает страницу с сервера, а не разбирает строки сам.

Таймер на экране считает браузер от `started_at` с поправкой на часы сервера. Поправку берём при загрузке страницы из RPC `server_now()`. База не обновляется каждую секунду.

## Онлайн-бронь без оплаты

Онлайн-бронь подтверждается сразу, без депозита. Защита от ботов и ложных броней:

- Cloudflare Turnstile на форме.
- Лимит активных онлайн-броней на один номер телефона и на один IP в заведении (`.env.example`). IP берётся из `x-forwarded-for` (первый адрес) или `x-real-ip`: на Vercel их выставляет платформа. За другим прокси он должен перезаписывать этот заголовок, иначе гость подставит свой IP и обойдёт лимит.
- Без `TURNSTILE_SECRET_KEY` проверка Turnstile пропускается только вне продакшена; в продакшене бронь без ключа не пройдёт.
- Число прошлых неявок гостя видно администратору, и он может отменить подозрительную бронь.

Депозит появится после первой версии. Таблицы `payments` и `bookings` спроектированы так, чтобы его можно было добавить новой миграцией без переделки существующих данных.

## Хранение данных и окружения

Закон РК «О персональных данных и их защите» (статья 12) требует хранить персональные данные в базе на территории Казахстана. Имена и телефоны гостей — персональные данные. У Supabase Cloud нет региона в Казахстане.

| Окружение | Где база | Данные |
| --- | --- | --- |
| Локальное | `supabase start` на компьютере разработчика | Seed |
| Демо | Supabase Cloud | Только тестовые |
| Пилот и продакшен | Свой Supabase (Docker) на сервере в Казахстане | Реальные |

Чтобы переезд на свой сервер прошёл без переделок:

- Все изменения схемы, функции, политики и задачи pg_cron только в миграциях.
- Настройки Auth и Storage описаны в `supabase/config.toml`.
- Не используем функции, которые есть только в Supabase Cloud.

Перед пилотом требования к хранению данных проверить с юристом.

## Безопасность

- RLS на каждой таблице, тесты на доступ чужого заведения в `supabase/tests`.
- `SUPABASE_SERVICE_ROLE_KEY` только на сервере.
- Ссылка управления бронью содержит случайный токен (не меньше 128 бит), а не id брони.
- Лимит активных онлайн-броней на один номер телефона и на один IP.
- Согласие гостя на обработку персональных данных сохраняется с датой (`customers.consent_at`).
- Журнал действий пишется триггерами в базе, а не из кода приложения, чтобы его нельзя было обойти.
